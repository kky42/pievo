# Remove Team Plan

## Status and execution rules

- Status: implemented and verified in the current uncommitted working tree.
- Do not create commits, tags, or branches. All work remains in the current working tree.
- Preserve and build on the existing uncommitted changes that removed `pievo new --connect-key` and `pievo new --server-url`.
- `packages/server/drizzle/0000_baseline.sql` is immutable. Schema removal must use a new forward migration.
- Do not commit generated Drizzle snapshots. TanStack's generated `src/routeTree.gen.ts` may be regenerated by typecheck and should only remain changed if route removal requires it.
- Server code remains zero-exec. Only the daemon executes providers.
- Authorization failures must remain enumeration-safe: another user's resource and a missing resource return the same externally visible result.

## Product decision

Pievo no longer has teams, workspaces, team membership, roles, invitations, or cross-user sharing.

The authorization model becomes:

| Mode | Identity and visibility |
| --- | --- |
| Auth mode | The signed-in `userId` is the sole tenant boundary. A user can see and manage only resources whose `userId` matches. |
| Open mode | There is no login identity. The server is one shared administrative workspace; every visitor who can reach it can see and manage every resource. Persisted open-mode resources continue to use the internal owner sentinel `shared` where a non-null `userId` is required. |

Machine/server identity and human authorization remain separate:

- Device tokens authorize one machine's daemon/CLI plane.
- Run tokens authorize report/help for one run.
- Web sessions in auth mode authorize only the matching human owner's resources.
- Network reachability is the security boundary in open mode; documentation must warn against exposing it unprotected to the public internet.

## Intended domain model

- `Machine.userId` is the only machine owner.
- `Loop.userId` is the only loop owner and must match the loop's machine owner at creation.
- Runs, snapshots, artifacts, and blobs inherit human authorization through their parent loop.
- Connect-key bindings contain only `{ userId, mintedAt }` and enroll one machine for that owner.
- `pievo new` always uses the active server connection; the server derives loop ownership from the authenticated machine.
- There is no API for sharing or transferring resources between users.
- In open mode, list and mutation APIs deliberately do not filter by `userId`.

## Existing data policy

The current schema already has non-null `user_id` columns on `machines` and `loops`. The migration therefore removes team data without rewriting ownership:

- Existing machines retain `machines.user_id`.
- Existing loops retain `loops.user_id`.
- Existing runs and artifacts remain attached to their loops.
- Existing shared-team collaborators lose access unless they are the resource's stored `user_id`; this is the intentional consequence of moving to per-user isolation.
- Existing open-mode rows with `user_id = 'shared'` remain shared through open-mode unfiltered access.
- Existing connect keys retain `connect_keys.user_id`; their `team_id` is discarded.
- Teams, memberships, and pending invitations are dropped.

This migration is destructive and not backward-compatible with older server binaries. Deployment guidance must require a database backup and coordinated server upgrade.

## Invariants after completion

1. No business schema table or TypeScript business type contains `teamId`/`team_id`.
2. No `teams`, `team_members`, or `team_invites` table remains in the current Drizzle schema.
3. In auth mode, every Web list/detail/mutation for machines, loops, runs, artifacts, and snapshots is scoped to the signed-in `userId`.
4. In auth mode, signed-out callers cannot mint connect keys or access resources.
5. In open mode, Web list/detail/mutation APIs intentionally operate across all server resources.
6. A device token can create and manage loops only for its own machine; a created loop uses `machine.userId`.
7. Another user's known loop, run, artifact, or machine identifier does not reveal that resource's existence.
8. Plaintext machine tokens remain visible only to the owning signed-in user in auth mode; open mode preserves shared visibility.
9. Scheduler, queue, lifecycle, protocol-v4 recovery, report outbox, and exact-artifact safety behavior remain unchanged.
10. No deleted team route, cookie, server function, component, or help/documentation reference remains.

## Subtask 1 — Database schema, migration, and store ownership APIs

### Schema

Update `packages/server/src/db/schema.ts`:

- Remove `machines.teamId` and `machines_team_idx`.
- Remove `loops.teamId` and `loops_team_idx`.
- Remove `connectKeys.teamId`.
- Remove `teams`, `teamMembers`, and `teamInvites` tables and their exported row/insert types.
- Keep `machines.userId`, `loops.userId`, and their indexes as the tenant fields.

Update `packages/server/src/db/index.ts` exports/imports accordingly.

### Forward migration

Add `packages/server/drizzle/0002_remove_teams.sql` and append its entry to `packages/server/drizzle/meta/_journal.json`.

The migration must:

1. Drop team-related indexes on machines and loops.
2. Drop `team_id` from `machines`, `loops`, and `connect_keys`.
3. Drop `team_invites`, `team_members`, and `teams` in dependency-safe order.
4. Preserve all machine, loop, run, artifact, receipt, lease, and blob rows.
5. Be valid for both Postgres and PGlite.

Do not edit `0000_baseline.sql` or `0001_add_pi_agent.sql`. Do not leave a generated snapshot.

### Store API

Refactor `packages/server/src/db/store.ts` and test helpers:

- Replace team-filtered loop listing/counting with user-filtered equivalents where auth-mode callers need them. Keep an unfiltered list for open mode and scheduler/server maintenance.
- Replace team-visible machine queries with owner-user queries. In auth mode machines are visible only when `machine.userId` matches.
- Remove all personal-team helpers and team/member/invite CRUD.
- Simplify machine and loop creation inputs so `teamId` is neither accepted nor defaulted.
- Simplify team-aware force-delete paths. Human authorization is checked by `userId`; store lifecycle deletion remains the durable authority transition.
- Ensure machine deletion still atomically handles its loops and revokes connect-key enrollment.
- Remove team imports from test store factories and seed data.

### Tests

- Update `schema.contract.test.ts` to assert the absence of team columns/tables and the presence/non-null ownership columns.
- Add migration coverage proving representative existing machine/loop/run/artifact rows survive `0002_remove_teams` with their `user_id` unchanged.
- Replace store team tests with owner-filter tests.

## Subtask 2 — Authentication and enumeration-safe user authorization

Refactor `packages/server/src/auth.ts`:

- Remove team cookies, `teamNameForEmail`, personal-team creation hooks, membership lookup, and explicit team selection.
- Reduce request scope to the minimum needed, for example `{ enforce, userId }`.
- Auth mode: signed-out scope has `userId: null` and never authorizes a resource.
- Open mode: authorization helpers return shared access without querying ownership.
- Replace `canAccessLoop(loopTeamId, scope)` with ownership authorization using `loop.userId`.
- Keep the GitHub login gate, allowlist, session secret requirements, and Better Auth behavior.

Refactor machine authorization:

- `packages/server/src/server/machineScope.ts` becomes owner-only in auth mode and all-visible in open mode.
- Remove team-machine thunks and membership joins.
- Preserve plaintext token visibility: owner-only in auth mode, shared in open mode.

Refactor loop/artifact authorization:

- `ownedLoop` authorizes by `loop.userId`.
- Raw artifact byte routes use the same ownership helper and remain enumeration-safe.
- Run and artifact endpoints continue authorizing through the parent loop.

Required tests:

- User A cannot list, detail, mutate, delete, run, or download artifacts belonging to user B.
- A known user-B identifier and a missing identifier produce the same outward result.
- Signed-out auth-mode requests cannot access resources or mint connect keys.
- Open mode can list and manage resources regardless of stored `userId`.
- Existing login allowlist and session-secret tests continue to pass.

- `ConnectKeyBinding` contains only `userId`.

- Keep token shape checks, TTL, durable binding, machine-id derivation, and deletion revocation.

Update `packages/server/src/gateway/index.ts`:

- Unknown-machine enrollment creates the machine with the binding's `userId` only.
- `createLoop` persists `userId: machine.userId` and no team field.
- Device-token authentication and machine scoping remain unchanged.
- Retain the current removal of create claims and target-server overrides.

Update machine and loop server functions:

- `mintConnectKey` accepts no team input and requires a signed-in user when auth is enabled; open mode binds to `shared`.
- Machine create/list/status/finalize/delete use current-user ownership in auth mode and shared access in open mode.
- Remove team-owner requirements from unreachable/force deletion; the machine or loop owner is the human authority.
- Device-side `store.forceDeleteLoop` remains the authority-retirement path.

Update daemon behavior only where stale team/claim wording remains. Do not change protocol v4 or daemon execution semantics.

Required tests:

- Enrollment binding records only the user and creates a machine for that user.
- `pievo new` creates a loop for the machine owner.
- A removed `claim` field is rejected as unknown.
- Auth-mode user B cannot manage user A's machine even if its ID is known.
- Open mode retains shared machine administration.
- Connect-key expiry/deletion revocation still works.

## Review checkpoints

### Review A — Data and migration safety

A reviewer must verify:

- baseline migration untouched;
- forward migration order and PGlite/Postgres compatibility;
- no business rows are unintentionally deleted;
- ownership semantics are deterministic (`user_id` retained);
- schema/store types match the migrated database;
- no generated Drizzle snapshots remain.

### Review B — Authorization and security

A reviewer must trace every Web entry point for loops, runs, artifacts, machines, connect-key minting, and destructive actions in both auth and open modes. It must specifically attempt cross-user known-ID access and signed-out auth-mode access.

### Review C — Lifecycle/protocol regression

A reviewer must confirm that scheduler, queue locks, pending/running uniqueness, lifecycle transitions, protocol v4 recovery, report outbox, exact artifact sync, and server zero-exec behavior were not changed.

### Review D — Product/UI cleanup

A reviewer must search for unreachable team UI/routes/types/copy and verify `/`, login redirects, dashboard loading, direct loop links, connect command generation, and open-mode warning behavior.
